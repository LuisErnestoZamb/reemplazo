# AGENTS.md

## What this is

- From-scratch OS written in **Rust** for a 2007 MacBook2,1 (hardware below). You are establishing structure, build, and test conventions; document them here as they land.
- Required deliverables, all in Rust in this workspace: kernel + low-level OS services, a command line (shell with **minimal builtins only** — not BusyBox/GNU/FreeBSD parity; grow on demand), an **opencode-like AI client with a VSCode-like editor**, a browser, **git** (clone/commit/fetch/push vs GitHub over ssh or https), **ssh client + server**, and an **installer**: bootable ISO **plus a network installer** (fetch the system over the network with the OS's own stack — sky2, DHCP, DNS, TCP/TLS).
- Dev happens on the **modern Mac (this checkout)**; the 2007 MacBook is the *target*, cross-compiled for. (opencode itself cannot run on the target — that's the point of the project.)

## Target hardware — hard constraints

- **CPU:** Core2 Duo T7400 (Merom, family 6 model 15), 2C/2T @ 2.16 GHz, x86-64 + VT-x, 4 MB L2.
- **ISA ceiling: SSSE3.** No SSE4.1, no SSE4.2, no POPCNT, no AVX → baseline is **x86-64-v1**. This is the single most important constraint in the repo.
- **RAM:** 2.9 GB DDR2-667 (2 slots, 4 GB max).
- **Disk:** 120 GB SATA 5400 rpm — the bottleneck. Budget runtime I/O accordingly.
- **Boot:** 32-bit Apple EFI running BIOS emulation → **GPT + `bios_grub` + GRUB i386-pc**. No macOS on disk; current Debian 13 install (~450 MB idle, IceWM + lightDM) is what this OS replaces.
- **Peripherals** (verified working under Debian — use these as hardware IDs when writing drivers):
  - GPU: Intel GMA950 (Xorg `intel`), 13.3" 1280x800
  - NIC: Marvell 88E8053 GbE (`sky2`) — wired + DHCP is the reliable dev path
  - WiFi: Atheros AR5418 a/bgn (`ath9k`) — radio OK, no credentials configured yet
  - Audio: HDA (`PipeWire` on Debian) · SMC/fan: `applesmc` + `coretemp`
  - DVD SuperDrive boots ISOs via **Option/C** — the primary way to test on real hardware
  - Bluetooth: present, disabled
- Network dev split (from the QEMU smoke scan): QEMU's NIC is **e1000** (`8086:100e`) — develop the TCP/IP stack against it; the MacBook's **sky2** (Marvell 88E8053, `11ab:4362`, constant `pci::SKY2_88E8053`) is *not* in QEMU, so the sky2 driver can only be validated on real hardware.

## Mistakes to avoid

- **Never build with `-C target-cpu=native`** or any host-feature detection: the build host is a modern Mac, the target is a T7400. Native code will emit SSE4+/AVX and die with SIGILL on the target. Pin the baseline explicitly (x86-64-v1 / no SSE4+ flags) and prefer `x86_64-unknown-none` (rustup-installable, `no_std`) over ad-hoc targets.
- **Don't plan an x86_64 UEFI bootloader or ESP.** Firmware is 32-bit EFI in BIOS-emulation mode; the boot chain is GRUB i386-pc → kernel. `x86_64-unknown-uefi` is the wrong path.
- **Don't assume headroom.** 2.9 GB RAM and a 5400 rpm disk rule out heavyweight runtimes, large indexes, and chatty logging at rest.
- **Networking is on the early critical path** (not "later"): clone/push vs GitHub, sshd, and the network installer all need sky2 → DHCP → DNS → TCP/IP → TLS 1.2+ / ssh (GitHub rejects legacy sha1 ssh-rsa). Prioritize the network stack accordingly.

## Workflow

- Git: branch `main`, remote `git@github.com:LuisErnestoZamb/reemplazo.git`. Commits: conventional (`feat:`, `fix:`, `docs:`, `build:`), one milestone per commit, message records what was actually verified.
- **Before every commit:** `cargo xtask check` (fmt + clippy for host crates *and* kernel target + host tests + kernel cross-build). Kernel is never linted/tested for the host — it is `x86_64-unknown-none` only.
- **Boot smoke test:** `cargo xtask smoke` — builds the ISO, boots it headless, asserts each milestone's serial marker in order (`BOOT_OK → VGA_OK → MEM_OK → ALLOC_OK → RTC_OK → PCI_OK → USB_KBD_OK → E1000_OK → NET_OK → PING_OK → DHCP_OK → DNS_OK → TCP_OK → TLS_OK → HTTP_OK → GIT_LSREMOTE_OK → GIT_FETCH_OK → SSH_KEXINIT_OK → SSH_KEX_OK → INT_OK → TUI_OK → EDITOR_OK → AI_CHAT_OK → BROWSER_FETCH_OK → AI_EDIT_OK → BROWSER_RENDER_OK → BROWSER_CSS_OK → BROWSER_NAV_OK → SHELL_OK → KEYBOARD_OK`) within 30s (boot phase) + 15s (keyboard phase). This is the test that catches broken boot (header/trampoline/paging/mbi), the VGA text mirror, frame-allocator, kernel heap (contiguous carve + global allocator + `Vec` proof), CMOS RTC, PCI-scan, UHCI enumeration + HID boot-keyboard descriptor/report parsing and set-1 translation (`usbwire`, `kernel/src/usb.rs`), e1000-driver, network-path, DHCP/DNS/TCP-client, TLS/HTTP-client, git ls-remote (smart-HTTP advertisement), git fetch (v0 upload-pack want/`deepen 1`/done POST → raw pack → `git-pack` header/zlib/delta/trailer decode + in-memory index → iterative commit→tree→blob walk with depth/entry/path caps), ssh key exchange (banner + `SSH_MSG_KEXINIT` algorithm intersection, then `SSH_KEX_OK`: curve25519 KEX + ed25519 host-key verify + pin + `NEWKEYS` + aes128-ctr/hmac-sha2-256 encryption + the `none` auth probe), interrupt (IDT/PIC/PIT), the screen layer (off-screen cell diff flush into the text buffer, ratatui `Backend`, full-frame readback from `0xb8000`), the editor (gap buffer + line index edits with undo/redo, viewport frame with gutter/status read back from `0xb8000`), the AI chat client (OpenAI-style request built and serde_json reply parsed over `net::http` POST against the in-container mock, chat-pane read back from `0xb8000`; **A4** adds a second `stream: true` exchange in the same proof against the mock's SSE responder on `10.0.2.2:8098` — three `delta.content` fragments rendered into the pane as they arrive, `[DONE]` required, accumulation and status read back from `0xb8000` — same `AI_CHAT_OK` marker, same chain position, no credentials), the editor↔AI integration (A5: the retained document quoted into a mock exchange, the completion applied at the editor cursor with an undo/redo round-trip asserted on the buffer, the resulting editor frame read back from `0xb8000`), the browser fetch (URL parse/resolve through `url` + redirect-following HTTP(S) GET against `github.com` — plain `301` hop resolved through `Url::join`, TLS hop, bounded body counted), the browser render (B2: `example.com` fetched through the parameterized B1 fetch, the `dom` HTML tree built over the tokenizer, the text layout — title bar, word wrap, lists, `<pre>`, inverse link cells — rendered in the viewport and read back from `0xb8000`), the browser CSS subset (B3: the `csscore` sheet parser + specificity/source-order/inline cascade, `display:none` skip, color→VGA-attribute mapping, bold/dim and margin/padding shifts — asserted on exact attribute bytes and positions in the styled fixture frame, and re-asserted as default attributes with the sheet removed, both read back from `0xb8000`; the real page's own stylesheet is applied as an unchecked robustness pass), the browser navigation app (B4: two kernel-owned fixture pages rendered/followed through `apps::browse`'s own keyboard path — the numbered link list selected with Tab and followed through `Url::join`, the selected link's highlight attribute, the bounded history's back/forward depths and its forward-tail-cleared-on-new-navigation rule, and the friendly **error page** an unreachable endpoint renders instead of halting — every step read back from `0xb8000`), serial-shell, or keyboard (i8042 bring-up → set-1 decode → line discipline → builtin; with the smoke's `usb-kbd` attached QEMU routes `sendkey` through the UHCI/HID wire into that same set-1 decoder) code, and — only when the attached FAT16 disk carries `/HOST.BIN` + `/AUTH.KEY` (the S5 sshd configuration; see the `smoke-ssh` bullet) — the server-side SSH session (KEX as responder, encrypted `publickey` auth against `/AUTH.KEY`, one `exec` channel; with no such files `sshd` prints nothing and listens on nothing, so the 30-marker chain is unchanged) code. `KEYBOARD_OK` is typed into the guest by xtask over QEMU's HMP monitor (`sendkey`, TCP port derived from the checkout path — see `qemu_std_args`); the marker must be the shell's `echo` output, not the input echo. QEMU runs with user-mode networking (`slirp`: guest 10.0.2.15, gateway 10.0.2.2, DNS 10.0.2.3 — constants in the `net` crate, asserted by the DHCP client). `DNS_OK`, `TCP_OK`, `TLS_OK`, `GIT_LSREMOTE_OK`, `GIT_FETCH_OK`, `SSH_KEXINIT_OK`, `SSH_KEX_OK`, `BROWSER_FETCH_OK` and `BROWSER_RENDER_OK` need working outbound network through Docker's resolver (they resolve and fetch `github.com`, and `github.com:22`), so the smoke test needs network access; `BROWSER_NAV_OK` is **offline** (kernel-owned fixture pages plus one deliberately refused connect to the slirp gateway), and `AI_CHAT_OK` and `AI_EDIT_OK` need **no internet** — they post to the chat mock xtask runs beside QEMU (slirp sends guest→10.0.2.2:8099 to the container's loopback).
- **Installer smoke test:** `cargo xtask smoke-install` — same ISO plus **two** 64 MiB images in `target/iso-root`: `disk.img`, a **valid FAT16 source volume** (magic pattern at LBA0 in the boot sector's boot-code area, offset 62 — see `kernel/src/ata.rs`; the BPB at 11..62 and the `55 AA` at 510 stay spec-shaped), and `target.img`, a blank target carrying only the wipe-marker magic `reemplazo-target-v1` (the installer refuses to format a disk without it — an unmarked second disk is ignored, never wiped). Both attach with `-drive file=/iso/<img>,if=ide,format=raw`, in order: source = master (unit 0), target = slave (unit 1), asserting `BLK_OK` … `FAT_OK` … `FS_WRITE_OK` … `FS_TREE_OK` … `INST_OK` … `GIT_CHECKOUT_OK` … `GIT_STORE_OK` … `NETINST_OK` (the ATA PIO probe of the legacy primary channel; the FAT mount + byte-exact `/README.TXT` read in `kernel/src/fs/` over the `fat` crate; the **write path**: the kernel writes `/RESULT.TXT`, re-mounts from scratch — a fresh `fat::Fat16` over a fresh block handle — and reads it back byte-exact while re-checking `/README.TXT` for clobbering; then the **I1 install flow** in `kernel/src/install.rs`: GPT written to the target with `gptwire` — protective MBR, CRC32 headers, entry-array caps, backup mirror — re-read and validated through the same parser, p2 formatted FAT16 through the **shared** `fat::format_fat16`, `/README.TXT`+`/RESULT.TXT` copied from the source volume, p2 re-mounted from scratch and read back byte-exact; the FS3 proof creates a three-directory LFN path and reads it back after a fresh re-mount (`FS_TREE_OK`), and G3's fetch checks the whole depth-1 tree out into the source volume (`GIT_CHECKOUT_OK`, 112 files / 53 dirs, byte-exact re-reads); then, after the boot network chain, `NETINST_OK` — the **network installer**: the kernel fetches `payload.tar` (the built kernel + README, served by the in-container `nc` responder on `10.0.2.2:8080` from `payload-http.txt`) **over its own stack** (smoltcp + `net::http`'s incremental parser into a bounded 2 MiB static), walks the ustar headers (checksum-validated, capped), reinstalls onto the same target and reads every file back byte-exact) within 30s. The target is probed **once before either proof** (the first install's protective MBR overwrites the wipe marker at LBA0). After QEMU exits, xtask **re-verifies `target.img` on the host** (GPT parsed independently + p2 mounted + the installed `/KERNEL.ELF` byte-exact against the **built kernel binary**). The main `smoke` runs with **no disk** — `ata::probe` prints nothing when no drive answers, `fs::prove`/`install::prove` are never reached (and `install::prove`/`netprove` return silently without a *marked* target), so its 30-marker chain is untouched. The driver is PIO/LBA28 reads *and writes*, **one single-sector command per transfer** (the multi-sector DRQ handshake is deliberately never assumed — I1 hit exactly that QEMU behavior), with every poll bounded, so it can never hang boot; `fat`'s writes are write-through (FAT → data → directory entry, no crash consistency yet — see `fat::write`). **I1b — the installed target is bootable** (`docs/installer.md` §8.6): `xtask iso()` builds GRUB's `boot.img` (512 B, copied from `grub-pc-bin`) and `core.img` (`grub-mkimage -O i386-pc -p '(hd0,gpt2)/boot/grub' -c <early.cfg>` with `biosdisk part_gpt fat multiboot2 normal search search_fs_file`) in the tools image, concatenates them as `grubpayload.bin` (`boot.img ‖ core.img` — the documented split at 512 B) and the ISO GRUB config loads it plus the kernel as multiboot2 **modules** (`module2 … grubpayload`, `module2 /boot/kernel.elf payload`). The kernel captures both into statics **before `memory::init`** (GRUB module frames are not reserved in the MBI memory map, so the heap would otherwise reuse them; `mbi::check_module` validates every range against a consumer cap — 1 MiB p1 for GRUB, the download bound for the kernel), and `install::install_grub` writes `core.img` to p1 with the block list recomputed (`start = 2048+1`, `len = sectors-1`, `segment = 0x820`, terminator at 488) and `boot.img` to LBA0 with the GPT protective MBR preserved and the same LBA patched at `0x5c` (unaligned u64 LE, `boot_drive=0xFF`, `0x66..0x68` = `nop;nop`) — `grub-setup`'s exact patch set — reading both back and re-checking `0xEE`/`55 AA`. Both installs (offline `INST_OK`, network `NETINST_OK`) end with that commit point; the offline install also writes `/KERNEL.ELF` from the ISO's `payload` module, so a disk installed without network still boots. After the install QEMU exits and `verify_installed_image` re-checks GPT + p2 + `/KERNEL.ELF` + the GRUB bytes against the ISO artifact, `smoke-install` runs a **second QEMU with `target.img` alone** (no ISO, `-boot order=c`, same e1000/USB devices, the chat mock still up for the kernel's fail-closed AI phase) and asserts `BOOT_OK → VGA_OK → MEM_OK → ALLOC_OK → RTC_OK → PCI_OK → E1000_OK → SHELL_OK` from the installed system (45 s; `SHELL_OK` implies every earlier fail-closed network/AI/browser phase passed). That boot has no installer source magic at LBA0 (GRUB's `boot.img` is there now), so `ata::probe` returns `None` and every disk marker is correctly absent — the neutrality rule seen from the other side. Remaining installer work: an editable p2 `/boot/grub/grub.cfg` + menu (the embedded early config boots the one entry directly, no `normal` UI), AHCI for the MacBook's ICH7 (the disk proof is QEMU IDE), the guided shell `disks`/`install`/`netinstall` builtins, the real `api.github.com` HTTPS payload fetch, and crash consistency around the GRUB write.
- **SSH server smoke test:** `cargo xtask smoke-ssh` — the two-VM end-to-end proof for milestone S5. One container runs **two** QEMUs started together. **VM1 (server)** boots with a FAT16 disk carrying `/HOST.BIN` (a per-run ed25519 host-key seed) and `/AUTH.KEY` (one `ssh-ed25519 <blob>` line: the *client* key); `kernel/src/sshd.rs` prints `SSHD_LISTEN_OK`, listens on guest `:2222` and answers banner → `KEXINIT` → `KEXDH_INIT/REPLY` (signature with the disk host key) → `NEWKEYS` → `SERVICE_REQUEST`/`USERAUTH_REQUEST` (`none` → `USERAUTH_FAILURE(publickey)`; the probe → `PK_OK`; the signed request verified over `session_id ‖ request` → `USERAUTH_SUCCESS`), then one `session` channel whose `exec` runs the tiny `echo` handler — `SSHD_KEXINIT_OK` … `SSHD_SESSION_OK`. **VM2 (client)** boots with the matching `/CLIENT.BIN` seed; after its normal network chain it dials `10.0.2.2:2222`: VM1 publishes guest `:2222` on the container loopback with `-netdev user,id=net0,hostfwd=tcp:0.0.0.0:2222-:2222`, which is exactly where VM2's slirp gateway leads. It authenticates, execs `echo SSHD_EXEC_OK`, prints `SSHD_OK` then `SSHD_EXEC_OK`. The keypair exists only inside the two disk images (`target/iso-root/sshd-*.img`, wiped by `iso()`), is never printed or committed; VM1's serial goes to the bind-mounted `target/iso-root/sshd-server-serial.log` (asserted by xtask), VM2's is the container stdout drained like `boot_assert`. Both QEMUs die with `docker rm -f` on every exit path. `cargo xtask smoke` / `smoke-install` are untouched: their disks carry neither file, so no listener and no line. The peer key is **TOFU for the session only** (signature verified, key + fingerprint printed; persistence is pending with the FS/`known_hosts` milestone), and the server serves **one connection per boot** (bounded 45 s accept) — a real accept loop needs the shell/scheduler beside it.
- Interactive boot: `cargo xtask run` (Ctrl-C quits; stale VM containers are force-cleaned on next run) drops into the serial shell — type `help`. Local terminals line-buffer, so for live echo run `stty raw -echo` in the terminal first. `run` also prints QEMU's monitor address (`127.0.0.1:<port>`) — inject keystrokes with `printf 'sendkey h\nret\n' | nc 127.0.0.1 <port>` (the QEMU `sendkey` path; the MacBook's real keyboard needs the UHCI/HID milestone).
- Single test: `cargo test -p mbi <name>`.
- **Progress reporting:** after every commit or completed milestone, the summary must include a "what remains" table (deliverable → milestone state → what's left), so the distance to "todo terminado" is visible at each step.
- Toolchain quirk (macOS 13, verified): no native `grub-mkrescue`, and Homebrew **cannot** build QEMU (Tier 3 → source build fails). Everything runs in the `reemplazo-tools` image (`tools/Dockerfile`: grub + xorriso + qemu); xtask prefers a host `qemu-system-x86_64` if one ever exists. Docker daemon must be running.
- `kernel` never builds with bare `cargo build` (excluded via `default-members`); it is built via `cargo xtask build` with `--target x86_64-unknown-none`.
- Verify against QEMU first; validate on real hardware via Option/C DVD or USB boot.
